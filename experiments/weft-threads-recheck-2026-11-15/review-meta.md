# What the review findings say, taken together

15 November 2026. Weft has been reviewed many times: every record in the experiments index carries a Review column, and today's reruns added more. This note counts the findings and asks what they have in common. The counts come from `meta/classify.py`, which reads `meta/findings.json` and `runtime/rows.tsv`. Its output is `meta/classify.out`.

## What was counted

- **93 findings** about records, pull requests and programs. 41 are from the Review column of the experiments index as of 14 November. 52 are from today's reruns.
- **154 sentences** of the weft README and Papers 0 to 2, each compared with the code or output it rests on.

Each finding has a kind and, where it makes sense, a direction: does the text claim more than the evidence, or less?

| Kind | What it means | Count |
|---|---|---|
| sentence | a sentence disagrees with the committed data or code | 22 |
| control | the favoured method gets information or tuning the comparison lacks | 14 |
| missing | no committed output, code that does not run, or a test never made | 13 |
| program | a defect in a program or instrument | 12 |
| scope | a proof, certificate or checker covers less than the sentence that cites it | 11 |
| order | the plan or pass bar was not shown to precede the data | 9 |
| packaging | a file, command or process step is wrong or absent | 8 |
| host | the result changes with the machine | 4 |

## Five readings

### 1. The numbers hold. What they are taken to mean does not.

Every committed result file that was re-run today came back the same: the nine probes of the thread record, the E13 certificate, the paper checks, the colony counts, the E15 benchmark and the E11 rerun. The exceptions are small: one split quoted in the colony tests file, and digest fields of E15 that depend on the maths library.

So the programs are not where the trouble is. Of the 93 findings, 12 are program defects. The other 81 are about what surrounds a number: the sentence, the comparison, the proof's reach, the order of events.

### 2. Research prose drifts up. Software prose goes stale and drifts down.

In the records and pull requests, 71 findings have a direction. **70 of them claim more than the evidence.**

The weft README and papers show the mirror image. Of their 35 problem sentences, 27 have a direction, and **20 claim less than the code now does**. The text says 12 shared test vectors where there are 27. It says the C test uses hand copies where it reads the shared file. It says a measurement was not made where the output is committed.

Both are the same failure. A sentence was true of some file at some time, and nothing ties it to that file. Where authors summarise their own results the slack runs upward. Where code keeps improving under fixed text it runs downward.

### 3. A sentence that a program regenerates was never wrong.

The sentence audit contains a natural experiment. The numbers in 68 sentences are regenerated by the paper checks that CI runs. **None of the 68 was wrong.** The other 86 sentences have no such tie, and **35 of them were wrong or unsupported**.

The claims register tells the same story from the other side. It marks rows as verified, by hand, once. Of 14 such rows, 10 are now stale or false.

These counts support one design rule. A sentence that carries a number or a verdict should be checked against its file by a program, every time the file or the sentence changes. `claims/check_claims.py` does that for this record. Issue 9 proposes the same idea as an expiry rule for the register.

### 4. The most damaging kind is the unfair comparison.

Fourteen findings are of the control kind: the favoured arm was handed the true permutation, or the true skill index, or thresholds fitted to the very cases it is scored on, or a task the host could already do.

Today's reruns tested this directly in two open pieces of work. In the E15 benchmark, an arm with the same information and none of the proposed machinery also passes 12 of 12. In the E11 rerun, an arm that transfers nothing matches the arm that transfers the plasmid. In both the reported advantage came from the harness.

A sentence ledger cannot catch this. A rule can: every record that claims a mechanism works must include an arm with the same information and without the mechanism.

### 5. A checker is only worth what a tampered input shows.

Eleven findings are of the scope kind. Two checkers in the project are independent in the full sense. The min-cut verifier on weft main rebuilds the network and rejected every tampered certificate it was given. The Farkas verifier recomputes both sides of its inequality.

The others re-read what they are given. `verify_e15.py` accepts a result that was edited and resealed, as its README now says. A Lean proof about integers stands beside a README about floating point.

The test that tells the two kinds apart is cheap: change a value, reseal, and see whether the checker objects.

## What would have caught what

| Gate | Kinds it addresses | Findings |
|---|---|---|
| Sentence ledger, run on every change | sentence, part of missing | 22 and up to 13 |
| Plan pushed before the run, with its commit named in the results | order | 9 |
| A no-mechanism arm required in every record | control | 14 |
| Tamper-and-reseal test for every checker | scope | 11 |
| Rerun on a second machine before the status is set | host | 4 |

The first two are mechanical and are used in this pull request. The preregistration of the calibration study was pushed before its run, and its results name that commit. The last three are review rules.

## Limits

- The 41 index findings are the index's own summaries of earlier reviews. They were not re-derived here.
- The kinds and directions were assigned by one reader. Another reader would move some findings between neighbouring kinds.
- The reruns were made by agent workers. The lead re-ran a part of them, listed in the record README.
- The sentence audit covers the README and Papers 0 to 2, not the site or the other papers.
